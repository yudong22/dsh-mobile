## 0. 速览

| # | 需求 | 真实病因（已定位） | 落点 |
| --- | --- | --- | --- |
| 1 | 扫新码后旧连接没保留 | `pairingProfile()` 整体覆盖 `endpoints` + 首个地址不匹配就新建 profile，旧机器从设备列表消失/连不上 | `AndroidMultiGatewayStore.kt` |
| 2 | 首页去掉项目标签 | 首页 `WorkspaceCard` + `WorkspaceSelectionMenu` 与底栏「项目」Tab 重复 | `DshProductApp.kt` |
| 3 | 抽屉「空间」默认收起、改名「项目」 | 默认 `spacesExpanded = true`；文案「空间」与产品语义（项目）不一致 | `WorkspaceDrawer.kt` |
| 4 | 抽屉任务列表按扫码机器缓存 | 会话列表**已**按机器隔离，但**工作区映射没有缓存** → 冷启动/离线无法按项目分组 | `GatewayPreferencesSnapshot` + 投影 |

**关键澄清（点 4）**：缓存**已经**按机器隔离了，不需要新建隔离机制——

- 会话列表：`AndroidGatewayPreferences(context, gatewayId)` → DataStore 文件 `host_$gatewayId`（`AndroidGatewayPreferences.kt:20`）
- 会话正文：`AndroidConversationCache(context, gatewayId)` → 目录 `gateway-conversation/$gatewayId`（`AndroidConversationCache.kt:28`）
- 凭据：`ScopedCredentials` → token key `host:$localId`（`AndroidMultiGatewayStore.kt:488`）

**真正缺的是** `GatewayPreferencesSnapshot` 只持久化了 `endpoint / selectedWorkspaceId / sessionsJson`
（`GatewayPlatformContracts.kt:84-88`），**没有 workspaces**。而抽屉分组完全依赖它：
`workspaceScopedSessions(sessions, workspaces, selectedWorkspaceId)`
（`DshProductApp.kt:589-604`）在 `workspaces` 为空时会把**所有**会话判为「未归属」。
所以点 4 = 「补上工作区映射的持久化」，而不是「引入按机器缓存」。

## 1. 点 1（bug）：扫新码后旧连接消失

### 1.1 根因

`AndroidMultiGatewayStore.pairingProfile()`（`:294-306`）：

```kotlin
val existing = profiles.firstOrNull {
    if (payload.gatewayId != null) {
        payload.gatewayId.equals(it.gatewayId, true)
    } else {
        it.gatewayId == null && endpoints.first() in it.endpoints   // ← 靠「首个地址」匹配
    }
}
val profile = existing ?: GatewayProfile(UUID.randomUUID().toString(), ...)
return profile.copy(endpoints = endpoints, preferredEndpoint = endpoints.first())  // ← 整体覆盖
```

两个独立缺陷：

- **缺陷 A（地址丢失）**：`endpoints = endpoints`（`:309`）是覆盖而非合并。命中 `existing` 时，
  旧机器原有的候选地址（例如远程 `wss://…`）被新扫码结果（本地优先 `ws://192.168.x.x`）整体替换。
  即用户观察到的「远程优先的服务器不在了」。
- **缺陷 B（身份漂移）**：`gatewayId == null` 的网关靠 `endpoints.first() in it.endpoints` 匹配。
  「远程优先」与「本地优先」两种二维码的 `publicUrl` 不同 → `endpoints.first()` 不同 →
  匹配失败 → `existing == null` → **新建 profile（新 `localId`）**。
  旧 profile 仍在 `profiles` 列表里，但它的 `preferredEndpoint` 指向已失效的远程地址，
  因此连不上、在线态为灰，在设备列表里表现为「彻底消失」。

**为什么这同时破坏点 4**：会话缓存挂在 `localId` 下（`host_$localId`）。
一旦 `localId` 漂移成新的，旧缓存全部对不上，切回去自然是空列表。

### 1.2 修法

优先级从高到低，建议 A+B 一起做：

- **[ ] A. endpoints 合并而非覆盖**
  `existing` 命中时，新地址与旧地址取并集（`preferredEndpoint` 指向本次可用地址），
  上限仍受 `MAX_ENDPOINTS = 16`（`:48`）与 `GatewayIdentity.endpoints` 的 `require` 约束。
  需要「保留仍在 `endpoints` 内的地址」语义，避免无界增长。
- **[ ] B. 让身份匹配不再依赖「首个地址」**
  在 `gatewayId == null` 时改为**整个 endpoint 集合求交**（而非 `first()`），
  并优先按 `gatewayName + 本地网段` 兜底；仍然无法判定时才新建 profile。
  更稳的做法是要求网关侧 `gatewayId` 非空——但那是协议变更，本版先做客户端侧兜底。
- **[ ] C. 迁移已有坏数据**：为已重复的 profile 提供去重/合并
  （同 `gatewayId` 或同 `gatewayName` 且地址有交集时合并，保留更早的 `localId` 以免丢缓存）。
  这是**数据修复**，必须在客户端做一次幂等迁移，否则老用户仍会看到重复条目。
- **[ ] D. 回归测试**
  - 单测：`pairingProfile` 对「同 gatewayId、不同 publicUrl 顺序」必须返回**同一个 localId**
    且 endpoints 为并集；
  - 单测：`gatewayId == null` 时，两个仅顺序不同的二维码必须命中同一 profile；
  - 设备测试：扩展现有 `MultiGatewaySmokeDeviceTest`（`scripts/multi_gateway_smoke_server.py`
    已在仓库里），先配对 A 再配对 B，断言 **A 仍在 `hosts.profiles` 中且可 select 回连**。

### 1.3 验收标准

- 连扫两次同一网关（一次远程优先、一次本地优先）后，`hosts.profiles` 里该网关**只有一条**，
  `localId` 与第一次一致，`endpoints` 同时包含远程与本地地址；
- 切换回旧机器，会话列表与工作区分组**立即可见**（来自缓存，不等网络）。

## 4. 点 4：抽屉任务列表按机器缓存

### 4.1 现状（与直觉不同，先澄清）

**已按机器隔离**的部分：

| 数据 | 隔离方式 | 位置 |
| --- | --- | --- |
| 会话列表 | DataStore `host_$gatewayId` | `AndroidGatewayPreferences.kt:20` |
| 会话正文 | 目录 `gateway-conversation/$gatewayId` | `AndroidConversationCache.kt:28` |
| 凭据/token | key `host:$localId` | `AndroidMultiGatewayStore.kt:488` |
| 选中项目 | `selectedWorkspaceId`（已持久化） | `GatewayPlatformContracts.kt:86` |

**缺口**：`workspaces` 不持久化（`GatewayPreferencesSnapshot` 没有该字段）。
后果：冷启动或离线时 `availableWorkspaces` 为空 →
`workspaceScopedSessions` 把所有会话归入「未归属」→ 用户看到的是**错误分组**
（不是空列表，这更容易被误当真）。

### 4.2 修法

- **[ ] A. 扩展 `GatewayPreferencesSnapshot`**，新增
  `workspacesJson: String?`（与 `sessionsJson` 同样的编码方式），
  并在 `AndroidGatewayPreferences.update()/toSnapshot()` 里读写。
  注意这是 **shared KMP 契约**（`shared/src/commonMain/.../GatewayPlatformContracts.kt`），
  改字段要同步检查 iOS 侧实现（`DeepSeekHarnessMobile/` 的 preferences 实现）。
- **[ ] B. 投影侧导出/恢复工作区**：仿照 `exportSessionCache` / `restoreSessionCache`
  （`AndroidGatewayProjection.kt:113`、`:146`）增加 workspace 快照的导出与恢复。
  恢复必须**只填列表、不发网络 effect**，且遵守 v1.8.2 里确立的
  「非网络基线」语义。
- **[ ] C. 尊重权威内容守卫**：恢复工作区时**不要**覆盖宿主已经推来的真实列表。
  可直接复用 v1.8.2 的 `hasAuthoritativeContent` 思路——工作区一旦收到过
  `workspaces` 帧，就不应再被缓存覆盖。
- **[ ] D. 选择 `最近使用` 的边界**：冷启动时 `selectedWorkspaceId` 可能指向缓存里已不存在的
  项目（宿主侧被删）。`activeWorkspace` 已有 `?: available.firstOrNull()` 兜底
  （`AndroidSharedStateHolder.kt:~1019`），需确认这条路径在缓存恢复后仍然正确。
- **[ ] E. 测试**
  - 单测：导出→恢复 round-trip 后 `availableWorkspaces` 与 `selectedWorkspaceId` 一致；
  - 单测：恢复后若宿主列表为空，分组结果与离线前一致（**点 4 的核心断言**）；
  - 单测：宿主推来 `workspaces` 帧后，缓存恢复不得覆盖它（沿用 v1.8.2 的守卫范式）。

### 4.3 验收标准

- 断开网络冷启动，抽屉按**上次的项目**正确分组会话，而不是全部落进「未归属」；
- 切换设备后，各自的分组互不串（依赖已有隔离 + 新增持久化）；
- 联网后宿主数据覆盖缓存，分组以宿主为准。

## 7. 风险与取舍
