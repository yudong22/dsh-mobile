## 1. 摸排：实测取证

### 1.1 「更多」按钮重叠并溢出（UI-1 的证据）

模拟器 `emulator-5554`（1080×2400 @420dpi，v1.9.5 在装）实测：

```
adb shell uiautomator dump  →  任务详情页页头节点
返回        bounds=[22,74][148,200]      126px 方（含投影）
标题        bounds=[258,81][822,150]     中心 (258+822)/2 = 540 = 屏宽一半 → 标题仍然居中
打开侧边栏  bounds=[943,84][1048,189]    ← 抽屉钮
更多        bounds=[985,74][1080,200]    ← 与抽屉钮重叠 63px，且右缘 = 1080 = 屏幕边界
```

结论（两条都实测）：
1. **两个按钮重叠**：`943..1048` 与 `985..1080` 相交 63px。
2. **「更多」紧贴甚至超出屏幕右缘**（右边界正好 1080），无右边距，与设计稿「贴右缘留 12dp」不符。

补充实测：点 `x=1015`（重叠区）会命中抽屉 → 抽屜打开；点 `x=1062`（仅「更多」区）才弹出菜单。
说明重叠区行为不确定，属于真实可用性缺陷。

**为什么标题没被推偏**：`DshPageHeader` 两侧槽位都用同一个 `sideSlotWidth`(`DshProductApp.kt:526,539,637`)，
所以标题仍居中；溢出的**只有按钮本身**。这解释了子审计无法判断的「裁剪还是偏移」——**是溢出，不是偏移**。

### 1.2 抽屉钮应回到返回钮右侧（UI-2 的证据）

`DshPageHeader` 的设计意图写在注释里（`DshProductApp.kt:500-503`）：

> 抽屉按钮（`onOpenDrawer`）与返回钮**互斥**：详情页包在抽屉宿主里时左侧是抽屉钮，返回改走系统返回手势。

而实现是 `when` 分支（`DshProductApp.kt:542-554`），**结构上无法同时渲染两个**。但：

- 你的原话：「后退按钮的**右边**添加一个展开抽屉的按钮」；
- 设计稿 `Docs/design/conversation-detail.html:34-37, 108-111`：`.side-slot{width:88px}`，**左侧放「返回 + 抽屉」**，右侧只放「更多」并贴右缘。

两者一致指向：**左侧槽位要能放两个按钮，右侧只放一个**，两侧等宽 88dp 保持标题居中。

### 1.5 三个可验证的性能热点

**(a) 附件可见性 effect 每 32ms 重启（PERF-1，最重要）**

`ConversationScreen.kt:808`：

```kotlin
LaunchedEffect(listState, items) {          // ← items 每个 token 都是新实例
    snapshotFlow { ... }.distinctUntilChanged().collect(stateHolder::updateVisibleAttachments)
}
```

同文件 `:773-779`（`ConversationScreen.kt`）已经为 markdown 预取修过**一模一样**的问题，并写明了机理：

> 预取 effect 只能以「结构」为 key。此前用 `timelineEntries` 本身作 key，而它每个 token
> 都是新实例，导致每 token 取消并重启 `snapshotFlow`、并重置 `distinctUntilChanged` 状态。

`items` 在滚动暂停关闭时按 32ms 节奏更新（`AndroidSharedStateHolder.kt:2579`），
所以这条 effect 每秒重启约 31 次，每次都：
- 重置 `distinctUntilChanged`，于是必然重新回调；
- 调 `updateVisibleAttachments`（`AndroidSharedStateHolder.kt:1917`），
  内部 `currentSessionAttachmentIds()` 展开**整个会话**的图片（同文件 `:2529-2530`）；
- `pruneAttachmentStateForSession()` 对两个缓存做 `retainKeys`（同文件 `:2431-2432`）；
- `publishAttachmentState()` 对整个缓存做两次 `mapKeys`（同文件 `:2552-2553`）。

**修法**：与 `ConversationScreen.kt:780` 的预取 effect 同构——key 用「结构性」的量（行数 / listState），
最新内容经 `rememberUpdatedState` 读取。

**(b) 每个 token 的 patch 是 O(行数)（PERF-2）**

`AndroidGatewayProjection.kt:799-803`：每个 `append-text` 都 `toMutableList()` 复制整个会话，
并重建 `indexById`。注释声称把定位降到 O(1)，但**每次 patch 的固定成本仍是 O(行数)**。
长会话（数百行）下这是每 token 的稳定开销。

**(c) 非 chunk 实时事件走全量重��影（PERF-3）**

`AndroidGatewayProjection.kt:600-605` 只为 `assistant/chunk` 跳过 `mobileStore.acceptFrame`；
其余事件都走 `AndroidGatewayProjection.kt:604` → `SharedMobileStore.makeSnapshot():734` 的 `ConversationProjector.make(全部事件)`。
且 `SharedMobileStore.acceptEvent():717-725` 每个事件都 `associateBy` + `sortedBy` 重排整表。

### 1.6 DATA-1 结案：同 seq 是**旧版网关**的形状，当前协议下**不存在内容丢失**

> 结论先给：**这不是一个活的 bug**。已核对主机与网关源码结案。
> 下面保留完整推演过程，因为它解释了「为什么代码里有这条绕过守卫的快通道」。

**最初的怀疑（我的探针实测）**：用一个临时探针（走生产路径
`AndroidGatewayProjection.acceptFrame`，跑完即删）回放同 seq 的 chunk，得到：

```
同 seq（seq=1 固定，delta 依次 "A" "B" "C"）：
  PROBE after 'A' -> lastError=null                      text='A'
  PROBE after 'B' -> lastError=conversation-event-failed text='B'     ← 报错
  PROBE after 'C' -> lastError=conversation-event-failed text='C'     ← 报错
  PROBE FINAL text='C' lastError=conversation-event-failed            ← 文本是 'C' 而非 'ABC'

不同 seq（seq=1,2,3）：
  PROBE DISTINCT text='ABC' lastError=null                            ← 正确
```

机制确实成立：`receiveEvent:53` 有 `require(record.seq > projector.lastSequence)` 守卫，
同 seq 抛异常后回退 `replaceSession` 全量重建并置 `lastError`。

**但「同 seq」这个前提只在旧版网关成立。核对源码后**：

| 事实 | 证据 |
| --- | --- |
| 主机 `seq` 是**逐事件** journal 下标，**不是** turn 级水位 | `deepseek-harness/packages/core/session/src/index.ts`：`seq: SessionSeq(this.log.length)` |
| 当前主机**根本不 append** `assistant/chunk` | `agent-loop/src/assistant-stream.ts` 发 `{attemptId, revision, index, ...}`，**无 seq**；`loop.spec.ts:107` 断言会话里不含 `assistant/chunk` |
| 当前网关发的是 `assistant-stream` 帧，**不带 seq** | `dsh-plugin-mobile-gateway/lib/index.mjs:3116-3118`；`session-follower.mjs:15`「No transient frame owns a Session seq」 |
| **旧版**网关确实每 chunk 复用同一 seq | 该网关自己的审计 `docs/dsh-0.1.5-rc.2-compatibility-audit.md` 明确记录了 `assistant/chunk seq=42` 连发三帧；`a8dbe57` 才修掉 |

**所以 `receiveStreamDelta` 与那句注释是为旧版网关写的兼容路径**：
注释里「同一 turn 内的所有 chunk 共享同一个 seq」描述的是**旧网关的行为**，
而不是主机语义——我已把该注释改写为如实描述（见 `SharedConversationStore.kt:69-89`）。

**当前协议下 streaming 的真实路径**（**不经过 `SessionEvent`**，因此无此问题）：

```
assistant-stream 帧 → bufferAssistantChunks → flushAssistantChunks
  → SharedConversationStore.assistantChunks → ConversationProjector.foldAssistantChunks
  → 按 attemptId + index 增量折叠（不是按 seq）
```

**结论与处置**：

- ❌ **不存在「用户看到内容丢失」的活 bug**——不要按高危处理，我之前的怀疑是**假警报**。
- ⚠️ 仍有一处真实的不一致：`receiveStreamDelta` **Android 从不调用、iOS 调用**
  （`AppStore.swift:3344-3345`）。这**不是内容正确性问题**，而是
  「旧版网关 + Android」组合下会走全量重建（性能退化）。当前网关下两条平台路径都走
  `assistantChunks`，**无差异**。
- 处置：**不在本版修**。仅保留正确的注释（已改），
  并把该方法的存废留给「是否还要支持旧版网关」这个产品决策。

**我从这次调查里收回的话**：第 0 节曾把 DATA-1 列为高危「文本被覆盖」。
经主机/网关源码核对，那是**旧路径**的形状，当前协议不可达。已在速览表中改判。

### 2.2 交互优化

#### [ ] UX-1：失败回答支持重试

- 现状：全仓只有 `retryAttachment`，**轮次级重发不存在**。
- 方案：新增 `resendLastTurn()`（或 `retryAssistantTurn(itemId)`）走既有发送通道重发上一条用户输入；
  失败行（`item.isError`）尾部给出「重试」入口。
- 风险：需要确认 host 是否接受重发（当前协议层无「重生成」语义）——
  若只能「重发同样的文本」，就把它如实标注为**重发**而非「重生成」，不要过度承诺。

#### [x] UX-2：发送键单一状态源（已实施）

- 现状：透明度与可点性各看一个信号，会出现「不透明但点不动」和「半透明但能点」。
- 方案：抽出唯一判据（`canSend`），容器底色在 `palette.primary` / `palette.disabledPrimary` 之间切换，
  **不用 alpha 淡化**——这正是 `DshTheme.kt:186-195` 记录的既有决策。
- 顺带补 `role = Role.Button`（`ContextUsageRing:2142` 与 `DshFab` 都有，发送键没有）。

#### [x] UX-3：页头副标题显示任务进度（已实施；刻意不写「后台任务」）

- 依赖 §2.4 的结论：**「后台任务」这个概念在协议里不存在**。
  唯一可用的是 `taskSnapshot`（= `todo_write` 投影），状态取值 `in_progress`/`completed`/其他=待处理。
- 因此副标题文案应如实写作**「N 个任务 · M 进行中」**，**不要写「后台任务」**——那会承诺一个不存在的功能。
- 数据源：`stateHolder.snapshot.taskSnapshot?.tasks`（`SharedMobileStore.kt:137-140`），
  计数逻辑与 `TaskGoalUi.kt:138-140` 保持一致，避免同页两处口径不同。

#### [x] UX-4：正文可复制（已实施）

- 现状：正文不可长按选择，只有尾部一个 16×26dp 的复制图标（`CopyButton:3009`）。

  - **B（更贴稿）**：`combinedClickable` 长按弹出「复制 / 用量 / 时间」，但**用量需先扩协议**（见 §2.4）。

#### [x] PERF-1（最高优先）：修掉每 token 重启的附件 effect（已实施）

#### [x] DATA-1：已结案（不改代码，仅修注释）

**结论**：不是活 bug。当前网关发不带 seq 的 `assistant-stream`，走
`assistantChunks` / `foldAssistantChunks` 增量折叠，**不经过 `SessionEvent`**，
因此不存在「同 seq → 回退全量 → 文本覆盖」的通路。详见 §1.6。

已做的唯一动作：把 `SharedConversationStore.receiveStreamDelta` 的注释从
「主机 seq 是 turn 级水位」（与主机源码不符）改写为如实描述——
主机 seq 是逐事件下标，同 seq 是**旧版网关**的合成行为。

**遗留（不在本版修）**：`receiveStreamDelta` 在 Android 无调用点、iOS 有调用。
这仅在「旧版网关 + Android」组合下造成性能退化（全量重建），
当前网关下两平台无差异。存废取决于「是否还要支持旧版网关」，属产品决策。

### 2.4 明确**不做**的事（以及原因）

这部分和方案同等重要——它避免把「做不到」包装成「已优化」：

| 项 | 结论 | 依据 |
| --- | --- | --- |
| 每条回答的 **token 用量** | **做不了**（投影里没有） | `ConversationItem` 仅 7 个字段，无 usage；`GatewayEvent.usage`(`GatewayDtos.kt:528`) 在投影层被丢弃；`ConversationProjector` 里 `usage` 出现 0 次 |
| 每条回答的**耗时** | 只能给**过程组**耗时 | `ConversationDisplayGroups.kt:222-226` 是分组首尾时间差，非单条回答 |
| 「**后台任务**」 | **该概念不存在** | 全仓无 `backgroundTask`/`subagent`；`taskSnapshot` 是 todo 列表 |
| 表格工具条（复制/转图片/展开/分享） | 本期不做 | 表格能渲染（markwon `ext-tables` 已接入），但工具条**代码里不存在**；「转图片/分享」需系统能力决策 |
| 折叠「已完成」行 | 待定 | 需要先定义展开后展示什么，否则是空壳 |

**若要做「逐条用量/时间」，正确路径是先扩协议**（host 下发 per-message usage），
那是协议改动，不属于纯 UI 优化，应单独立项。
